# Findings — 2026-08-04

## A1. A derived Dataset does not recompute when its source region is written

**Status: OPEN. Blocking** the tracker's clock removal (§A2 below).

A `Dataset [ contents = { … } ]` whose body reads another dataset's region is
statically wired to that region and still does not recompute when the region is
written. Twelve lines:

```declare
App [ width = 10, height = 10,
    db: Dataset { { "issues": [] } },
    q: string = "",
    rowsOf() -> array { return db.value.issues ?? [] },
    proj(query: string) -> object { return ({ rows: this.rowsOf(), total: this.rowsOf().length }) },
    shown: Dataset [ contents = { app.proj(app.q) } ],
    total: number = { (app.shown.value.total ?? 0) }
    ]
```

```
shown.contents   static=true  deps=["this.root.q", "this.root.db.value.issues"]

db.set(["issues"], 3 rows)   → shown.value = { rows: [], total: 0 }   STALE
app.proj(app.q) called now   → { rows: [3 rows], total: 3 }           correct
app.q = "x"                  → shown.value = { rows: [3 rows] }       recomputes
```

So the dependency is extracted, listed, and visible in `explain()` — and touching
an ordinary slot dep wakes it — but the region write does not. The method is fine;
the constraint simply never re-runs.

**What it is not.** Not a dep-extraction failure: `this.root.db.value.issues` is
right there in the wired deps. Not a method-following failure either — a plain
slot doing the same read (`counts: object = { app.countStatuses() }`) updates
correctly, because it falls to runtime tracking. The difference is the derived
DATASET, whose recompute is dep-gated by design (`schema.ts`, DatasetSchema: "a
derived collection: recompute is dep-gated"). `db.set(["issues"], …)` does not
open that gate.

**A near miss worth recording, so the next person does not repeat it.**
`bind.ts` decides prewire-vs-track with

```ts
const regionReactive = deps.some((rp) => rp.startsWith(":") || rp.includes(".read("));
```

which recognizes two spellings of a region read and misses a third: an ordinary
property chain, `db.value.issues`. Adding `.value.` to that test looks like the
fix and is not — it moves the constraint to the tracking path, where it is *still*
stale, and costs the static deps that at least woke it on `q`. Whether the
predicate should recognize the third spelling anyway is a separate question; it is
not this bug. The gate is downstream.

## A2. The tracker's `rev` clock is load-bearing, not defensive

`apps/tracker/tracker.declare` threads a mutation counter through nine method
parameters — `project(rev, byStatus, byAssignee, …)`, `issuesOf(r)`, whose `r` is
never used — and every verb bumps it after writing `db`. The comment at :750 says
why: *"bodies are unanalyzed by design"*.

**That reason is false.** A method reading `db.value.issues` wires
`this.root.db.value.issues`, measured. But removing the clock on that basis breaks
the app — 12 of 15 tracker tests fail, the projection empty at boot — because §A1
means the wired region dep never fires. The clock is the only thing making the
projection recompute.

So the cleanup is real and worth doing (the clock is one coarse signal for all
data: every mutation recomputes every projection — the list, the counts, the
burndown, the workload — where region deps would wake only what read the changed
region, in the app that exists to demonstrate performance). But it is **gated on
§A1**, and the comment should not be corrected in isolation either: it is wrong
about the mechanism while right that the clock is needed.

Attempted 2026-08-04, reverted intact.

**`groupRev` is different and must stay.** The collapse state lives in
`(this as any)._collapsed`, a plain array with no cell, so nothing can notice it
change — that is a clock doing its actual job. The fix there, if wanted, is to make
the collapsed set a real reactive slot, not to remove the counter.

## B1. Tooltips were anchored to the unscrolled position — FIXED

`tip.ts publish()` summed ancestor x/y by hand. Measured: inside a pane scrolled
300px, a target SEEN at y=140 put its tooltip at y=309 — anchored to y=340, where
the target would have been unscrolled. Now uses `rootFrameOrigin` (the shared
walk), and the tooltip lands at y=187, just below the target.

This is the third consumer to hand-roll that walk: the Inspector's highlight
(fixed when `rootFrameOrigin` was extracted *because* of it), `inspect()` (fixed
2026-08-03), and this. The shared function's own comment already warns against
hand-accumulating; that has not been enough to stop it recurring, which is worth
weighing if a fourth appears.
