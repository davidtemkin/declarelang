Layout comprehension probe

The question: does the rewritten layout section of declare.md teach agents the layout model better than the old one? The way to find out: eight fresh agents, half on each text, each asked to predict and then write layouts with no way to run them. The answer was mostly no. The probe's real yield was two runtime bugs, both hit by correct code. Both are fixed, along with a bug in the forms library that Venue 17 ran into.

In brief

Both texts teach the rules

On five of the six prediction questions, all eight agents answered correctly under either text. The new text did steer every agent to a State for a size that holds only sometimes; under the old one, two of four used a conditional constraint instead.

The failures were the runtime's

Two frames refused at boot looked like old-text misunderstandings. They were valid code hitting a layout bug. A second bug hit every new-text frame. With both fixed, every program in both arms has correct layout.

Venue's first-boot layout failures came from elsewhere

On focused tasks the agents got stretch and filling right. Venue 17's content-sized fields and NaN-as-unset likely come from a large build, where the rule gets lost among everything else, or from bugs like these two.

How the probe worked

  1. Two copies of the docs, nothing else different. The control arm had declare.md as committed (c5a44f81). The other had the rewritten §4, the corrected §6 and the amended difference #5. Each agent's folder held only README.md and docs/declare.md.
  2. Eight fresh agents, four per arm (Opus 5.5, headless). Each was told to read those two files in full and nothing else. It had file tools only: no shell, no compiler, no browser. What it wrote is its first attempt.
  3. Part A, six predictions: how wide a child is in a column; how to make children as wide as the widest; flexes plus a width; a size that holds only sometimes; what to write on a child whose layout's axis is computed; and 100% in a parent sized by its children.
  4. Part B, three programs, all generic: a window frame whose side panel moves under the list below 600 wide; a form whose fields fill a 360 column, with two sharing a row; a menu whose items are as wide as the widest label.
  5. Scoring. Each program went through declare-verify at phone and desk sizes. Its laid-out geometry was then read back and checked against the task: the panel 240 wide and full height on desk, 120 tall and full width on phone; fields 360; menu items equal. The answers were read against what the runtime actually does, and each claim in the new text was checked with a small program of its own.

Two runtime bugs the probe found

1. A size stated by a constraint was refused under align = stretch

A child of a stretching layout that states its own size should keep it. The guide says so, and a constant did: width = 300 stayed 300. But any constrained width, even { app.wide ? 300 : 200 }, was refused at boot as a conflict with the layout. A constant exists before the layout installs, so stretch leaves that child alone. A constraint binds after, finds the layout's stretch claim already on the slot, and was treated as two deciders.

col: View [ width = 400, layout: SimpleLayout [ axis = y, align = stretch ],
    constant: View [ width = 300 ],                       // kept: 300
    computed: View [ width = { app.wide ? 300 : 200 } ],  // was refused at boot; now 200
    content:  View [ ] ]                                  // stretched: 400

This is what refused the two old-text frames. Their code, width = { narrow ? parent.width : 240 }, was correct.

Fixed: a stretch claim is marked as filling only a size left to the content, and a size the author states now takes the slot from it, whether as a constraint or a handler's write (attributes.ts, plus one flag in reactive.ts and layout.ts). Regression test in layout-facts.

2. A size a State released was not stretched under a computed axis

This is exactly the pattern the new text teaches: a State for the size that holds only sometimes, inside a layout whose axis flips with the window. At boot the window width isn't known yet, so narrow is briefly true and the narrow-screen State sets the panel's height. The layout installs against that, deciding the height isn't its to fill. When the width arrives the State lets go, but nothing tells the layout, so the panel falls back to its text's height: 34 instead of 720.

body: View [ flexes = true,
    layout: SimpleLayout [ axis = { app.narrow ? "y" : "x" }, align = stretch ],
    list: View [ flexes = true ],
    side: View [ beside: State [ applied = { !app.narrow }, width = 240 ],
                 under:  State [ applied = { app.narrow },  height = 120 ] ] ]
// desk: side was 240×34; now 240×720

Fixed: when a State releases a size and nothing claims it once the settle is over, the parent's layout installs again (state.ts). A first version reinstalled every time and broke the fixed-axis case, where the layout already holds a claim. The fixed-axis case is now in the check and in the tests. Regression test in layout-facts; it fails on the old runtime.

The forms bug from Venue 17

On a wrong security code the service refuses, and Venue 17 emptied the code so it would be asked for again. Form.refusedWith's own docs give that as the example. But Form laid the refusal on the field first and ran refusedWith after. A refusal counts only while the field holds the refused value, so emptying the field erased the service's message.

Fixed in form.declare only: refusedWith runs first. Once what it changed has settled into the fields, the refusal is laid on them, and a field that receives one is judged, so its message shows. The controls and the runtime are unchanged, and every step is still the developer's to override. Venue 17's app, unchanged, now passes 11 of 11 hidden flows (it was 10); Venue 16's still passes 11 of 11.

The text that changed

Before: §4 "Layout is an attribute"

There is no <Stack>, no <Row>, no flexbox, and no grid. A view positions its children absolutely by x/y until you set a layout: member — and because that member is an ordinary reactive attribute, it can be swapped, derived, or animated. A layout places its children, and what it places a child does not declare: a row places x, align adds y, a ResponsiveLayout places both; a child that declares one anyway is refused at its line, in any spelling. A child asks the layout for a size by stating a fact — flexes, shrinks, a minWidth/maxWidth range — and align = stretch makes what its content would size fill the view across.

After

Each of a view's x, y, width and height has one decider: its content, the view itself, or its parent's layout. A layout is an object, not a mode: a library class (SimpleLayout, WrappingLayout, ResponsiveLayout) or a class of your own with one method, set as the view's layout: member and swapped like any member. A child never states what its parent's layout decides. It tells the layout facts about itself — flexes, shrinks, a minWidth/maxWidth range — and the layout, seeing every child, places them all and sizes the ones that ask.

A size left unset is the content's, inside a layout too. Unlike flexbox, nothing stretches unless the layout says align = stretch. A size travels one way: a view sized by its children can't also size them, which would be circular, so children fill such a view by align = stretch, as wide as the widest. A constraint always decides, so a size that holds only sometimes is a State.

Also changed: §6 said a view has no minHeight or maxHeight, which stopped being true when the ranges arrived; difference #5 now names a State for a configuration that changes.

One wording issue: two new-text agents concluded from "a constraint always decides" that you can't write "otherwise the content's width" as a constraint. Outside a layout, { wide ? 300 : contentWidth } works, and after fix 1 it also works inside one. The sentence is fine as advice, but it could be softened so it doesn't read as a prohibition.

What this suggests

  • The model is teachable from declare.md as it stood. On focused questions both texts produced correct predictions. The rewrite is clearer and steers toward State, but it doesn't explain Venue's first-boot failures.
  • Runtime inconsistencies look like misunderstanding. Both bugs refused or mis-sized correct code, and in a full build an agent reads that as its own mistake and works around it. Some of what earlier runs called layout difficulty may have been this.
  • Comprehension probes are cheap and sharp. Eight short runs found two core bugs that a dozen full app builds had not isolated. Generic tasks keep them from teaching to any one eval.
  • What's left from Venue 17 (fields sized to their content, NaN as unset) appears only in a full build. A recorded Venue 18 on the fixed runtime would show whether it persists.
