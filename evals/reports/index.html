How a run is scored

The acceptance is written before a solution exists and is never shown to the solving agent — an acceptance authored afterwards grades on a curve. It addresses the program by what is on screen and what happens when you click it, never by the identifiers a particular solution chose, so any implementation shaped to the brief can pass. The service is deterministic, and the harness resets it before each run.

How findings are handled

An agent's report is evidence, not a conclusion. Every claim is reproduced here against the same commit before it is recorded, and each carries one of four dispositions:

Fix bug Docs update New feature Ignore

Claims that fail re-testing are kept in the report, marked Rejected or Not reproduced, so nobody chases them twice. Both runs on this page contain examples of each — including defects in the eval harness itself, which are recorded rather than quietly fixed.

The findings of this round. Three agents independently hit the same defect: a DataSource whose URL is set in the same handler that fetches it requests the old address, and the documentation says the opposite. And the second Cadence run found the sharpest defect the programme has produced — d.w / d.h, documented and type-checked, silently drawing nothing. Validated reproductions for everything are in 2026-08-05-bugs.md.

Reports are generated per run and kept with the code each run wrote. Source apps and briefs live under evals/apps/; the run trees themselves are disposable.
