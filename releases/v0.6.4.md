# a layout goes with the children it is written with

This release undoes 0.6.3's breaking change, which was a mistake, and fixes the bug that
prompted it. A class that names a `defaultPlacement` (a `Sheet`, a `Popover`, a class of your
own) puts the children a subclass or a use site writes into the child it names, and a
`layout:` written with those children goes there too and arranges them. That was the rule
before 0.6.3, and it is the rule again. The class's own children keep the layout the class
gives them: that is the fix. Before 0.6.3 a layout written with the placed children took the
class's own layout with it, and the class's own children were left unarranged.

## Breaking changes

### a View around placed children for their layout → the `layout:` written with them
A `layout:` written with the children a class places arranges them where they go; 0.6.3 made it arrange the class's own children instead.

```declare-fragment
Popover [
    View [ layout: SimpleLayout [ axis = x, spacing = 8 ],
        Text [ text = "One" ], Text [ text = "Two" ] ] ]
```

```declare-fragment
Popover [ layout: SimpleLayout [ axis = x, spacing = 8 ],
    Text [ text = "One" ], Text [ text = "Two" ] ]
```

Docs: [`View.defaultPlacement`](declare-docs:View.defaultPlacement) · [`View.layout`](declare-docs:View.layout)

Watch for: nothing to change if you moved to 0.6.3 by wrapping your content in a View, which still works. A `layout:` you wrote under 0.6.3 to arrange a class's own children now arranges the children you placed instead.

## Smaller changes

- A class with a layout of its own keeps it when a subclass or a use site writes a layout for
  the children it places. A message row stacking its bubble above its time, whose subclass laid
  out its own controls in a row, lost its column and drew the time over the bubble.
